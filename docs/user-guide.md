# 사용자 가이드

이 문서는 **컴파일러 최적화 옵션 비교기**를 실제로 써보고 싶은 사람을 위한 안내서입니다.
코드 구조가 아니라 "어떻게 실행하고, 화면을 어떻게 읽으면 되는지"에 초점을 맞췄습니다.
(개발자용 코드 설명은 [backend.md](./backend.md), [frontend.md](./frontend.md) 참고)

---

## 1. 이 앱은 무엇을 하나요?

C 코드를 입력하면, 선택한 컴파일러(**Clang** 또는 **GNU GCC**)가 최적화 수준(`-O0`, `-O1`, `-O2`, `-O3`)을
다르게 적용했을 때
- 생성되는 **어셈블리 코드**가 어떻게 달라지는지
- **컴파일된 코드 크기**가 얼마나 줄어드는지
- **컴파일 시간**이 얼마나 걸리는지
- (옵션) **실제 실행 시간**이 얼마나 빨라지는지

를 네 개 열(column)로 나란히 보여줍니다. "컴파일러 최적화가 대체 뭘 하는 거지?", "clang이랑 gcc는
같은 코드를 어떻게 다르게 최적화하지?"를 눈으로 직접 확인해보기 위한 학습용 도구입니다.

## 2. 처음 실행하기

### 준비물
- macOS (Xcode Command Line Tools에 포함된 `clang`을 사용합니다)
- Java 17 이상, Maven (백엔드용)
- Node.js, npm (프론트엔드용)
- (선택) GNU GCC — `brew install gcc`로 설치하면 컴파일러 드롭다운에 "GNU GCC"도 뜨고 선택할 수
  있습니다. 설치 안 해도 앱은 정상 동작하며, 이 경우 드롭다운에는 Clang만 나옵니다.
  > ⚠ macOS 기본 `gcc` 명령은 사실 Apple clang의 별칭이라 진짜 GCC가 아닙니다. 서버가 자동으로
  > 이를 걸러내므로, 진짜 GCC와 비교하려면 반드시 Homebrew로 설치해야 합니다.

준비물이 설치되어 있는지 확인하려면:
```bash
clang --version
mvn --version
node -v
gcc-16 --version   # brew install gcc로 설치한 경우 (버전 번호는 설치 시점에 따라 다를 수 있음)
```

### 백엔드 실행 (터미널 1)
```bash
cd backend
mvn spring-boot:run
```
`Tomcat started on port 8080` 같은 로그가 뜨면 준비 완료입니다.

### 프론트엔드 실행 (터미널 2)
```bash
cd frontend
npm install   # 처음 한 번만
npm run dev
```
터미널에 뜨는 주소(보통 `http://localhost:5173`)를 브라우저에서 열면 됩니다.

> ⚠ 백엔드와 프론트엔드를 **둘 다** 띄워야 정상 동작합니다. 프론트엔드만 켜져 있으면
> "비교하기"를 눌러도 요청이 실패합니다.

## 3. 화면 사용법

### 3.1 코드 입력
1. 화면 위쪽의 검은 텍스트 박스에 C 코드를 입력합니다. (처음 접속하면 예시 코드가 미리 채워져 있습니다)
2. `main()` 함수는 없어도 됩니다 — 이 앱은 실행 파일이 아니라 **오브젝트 파일(.o)** 을 기준으로
   크기를 비교하기 때문에, `square(int x)`처럼 함수만 있어도 됩니다.
3. **컴파일러** 드롭다운에서 사용할 컴파일러를 고릅니다. 서버에 설치되지 않은 컴파일러는
   회색으로 비활성화되어 선택할 수 없습니다.
4. 실제 실행 시간까지 보고 싶으면 **실행 시간 측정** 체크박스를 켭니다. (자세한 내용은 3.4절 참고)
5. **비교하기** 버튼을 클릭합니다.

### 3.2 결과 읽는 법

버튼을 누르면 아래에 `-O0`, `-O1`, `-O2`, `-O3` 네 개의 박스가 나란히 나타납니다.

```
┌─────────────┬─────────────┬─────────────┬─────────────┐
│ -O0 ⓘ       │ -O1 ⓘ       │ -O2 ⓘ       │ -O3 ⓘ       │
│ 712B · 52ms │ 648B · 38ms │ 648B · 35ms │ 648B · 35ms │
│ (기준)       │ (+19/-39)   │ (+19/-39)   │ (+19/-39)   │
├─────────────┼─────────────┼─────────────┼─────────────┤
│ 어셈블리 코드 │ 어셈블리 코드 │ 어셈블리 코드 │ 어셈블리 코드 │
│  (기본 색상) │ (바뀐 줄은  │ (바뀐 줄은  │ (바뀐 줄은  │
│             │  초록색)    │  초록색)    │  초록색)    │
└─────────────┴─────────────┴─────────────┴─────────────┘
```

각 박스 안 요소들의 의미:

| 요소 | 의미 |
|---|---|
| **레벨 이름 옆 ⓘ 아이콘** | 마우스를 올리거나(또는 Tab 키로 포커스) 하면 그 최적화 레벨이 뭘 하는지 설명이 뜹니다. `clang -O0`~`-O3`가 뭔지 아직 익숙하지 않다면 여기부터 읽어보세요. |
| **크기 (예: 712B, 648B)** | 그 레벨로 컴파일했을 때의 오브젝트 파일 크기. 숫자가 작을수록 컴파일된 코드가 더 압축됐다는 뜻입니다. |
| **시간 (예: 52ms)** | 그 레벨로 컴파일하는 데 걸린 시간(어셈블리 생성 기준). 최적화를 많이 할수록 컴파일 자체는 더 오래 걸리는 경향이 있습니다. |
| **(+19 / -39 vs O0) 배지** | `-O0` 대비 몇 줄이 새로 생기고(+) 몇 줄이 사라졌는지(-)를 나타내는 요약입니다. O1~O3에서만 보이고, 기준이 되는 O0에는 표시되지 않습니다. |
| **초록색으로 강조된 줄** | `-O0`의 어셈블리에는 없던, 이 레벨에서 새로 생기거나 바뀐 줄입니다. 최적화가 "구체적으로 어디를 바꿨는지" 여기서 확인할 수 있습니다. |
| **강조되지 않은 줄** | `-O0`에도 똑같이 존재하는 줄 — 이 레벨에서는 그대로 유지된 부분입니다. |

### 3.3 실전 예시로 읽어보기

기본으로 채워지는 예시 코드에는 `square(int x) { return x * x; }` 함수가 있습니다.

- **-O0**: `x`를 스택에 저장했다가 다시 읽어서 곱하는, 사람이 짠 코드와 거의 1:1로 대응하는 비효율적인 어셈블리가 나옵니다.
- **-O1부터**: `mul w0, w0, w0` 단 한 줄로 줄어듭니다. 스택에 저장하고 다시 읽는 불필요한 과정이 통째로 사라진 거죠.
  이 줄이 바로 초록색으로 강조되어 보이는 부분입니다.

이런 식으로 "내가 짠 코드가 실제로 어떻게 최적화되는지"를 함수별로 비교해보면 좋습니다.

### 3.4 실행 시간 측정 (옵션)

**실행 시간 측정** 체크박스를 켜고 비교하면, 각 박스 메타 정보에 `⏱ 실행 3.42ms`처럼
실제로 실행해서 걸린 시간이 추가로 표시됩니다.

- 동작 방식: 서버가 O0~O3 각각을 실제로 **링크해서 실행 파일을 만들고, 5번 실행해서 그중
  가장 빠른 시간**을 채택합니다. 이 기능은 `main()` 함수가 있어야만 동작합니다.
- `main()`이 없는 코드(예: 기본 예시처럼 함수만 있는 코드)는 체크박스를 켜도 링크 자체가
  안 되므로, 컴파일/어셈블리 결과는 그대로 보이고 실행 시간 자리에는 회색 `⏱ 실행 불가`
  배지만 뜹니다. 오류가 아니라 정상적인 동작입니다.
- ⚠ 이 기능은 **서버가 사용자가 입력한 코드로 만들어진 프로그램을 그대로 실행**합니다.
  그래서 기본값이 꺼져 있고, 사용자가 직접 켜야만(옵트인) 동작합니다. 신뢰할 수 없는 코드를
  이 앱에 붙여넣고 실행 시간 측정을 켜지 마세요.
- 짧고 단순한 함수는 프로세스를 띄우고 종료하는 오버헤드가 실제 연산 시간보다 훨씬 커서,
  O0~O3 간 실행 시간 차이가 잘 안 보일 수 있습니다. 반복 횟수가 많은 루프가 있는 코드일수록
  최적화 레벨 간 차이가 더 뚜렷하게 나타납니다.

## 4. 컴파일이 실패했을 때

문법 오류가 있는 코드를 넣으면 각 박스 위쪽에 빨간색 **"컴파일 실패"** 배지가 뜨고,
본문에 clang이 알려주는 원본 에러 메시지가 그대로 표시됩니다.

```
⚠ Clang (LLVM)가 이 코드를 컴파일하지 못했습니다
input.c:1:16: error: use of undeclared identifier 'retrun'; did you mean 'return'?
```

에러 메시지 형식은 `input.c:줄번호:칸번호: error: 설명` 입니다. 위 예시는
"1번째 줄, 16번째 칸에 `retrun`이라는 오타가 있다(→ `return`을 의도한 것 같다)"는 뜻입니다.
이 정보를 참고해서 코드를 고친 뒤 다시 **비교하기**를 눌러보세요.

### 코드 입력란을 비운 채로 제출하면?
화면 위쪽에 `⚠ C 코드를 입력해주세요.` 라는 안내가 뜹니다. 코드를 입력하고 다시 시도하세요.

## 5. 자주 묻는 질문 (FAQ)

**Q. `-O2`와 `-O3`의 어셈블리가 똑같이 나올 때가 있어요. 버그인가요?**
아닙니다. 짧고 단순한 함수는 `-O2`에서 이미 최대로 최적화되어서, `-O3`이 추가로 적용하는
루프 벡터화 같은 고급 최적화가 적용될 여지가 없는 경우가 많습니다. 루프가 많거나 반복 연산이
있는 코드를 넣으면 `-O3`에서만 나타나는 차이를 볼 수 있습니다.

**Q. 크기가 0으로 나와요.**
`-O0`처럼 값이 정상적으로 나오는 레벨과 함께 0이 나온다면 버그일 수 있으니
[docs/backend.md](./backend.md)의 `CompilerService`를 참고해 오브젝트 파일 생성 과정을 확인해주세요.
정상적인 코드라면 보통 0이 나오지 않습니다.

**Q. "비교하기"를 눌렀는데 아무 반응이 없어요 / 네트워크 에러가 떠요.**
백엔드(8080번 포트)가 꺼져 있을 가능성이 높습니다. [2. 처음 실행하기](#2-처음-실행하기)를 참고해
백엔드가 켜져 있는지 확인하세요.

**Q. 다른 컴퓨터에서도 똑같이 동작하나요?**
최소한 `clang`이 설치되어 있어야 하고, macOS/Linux의 컴파일러 버전이나 CPU 아키텍처(Intel/Apple Silicon 등)에
따라 생성되는 어셈블리 문법이 달라질 수 있습니다(예: x86과 ARM은 완전히 다른 명령어 집합을 씁니다).
같은 컴퓨터, 같은 컴파일러 버전으로 비교하는 것을 권장합니다.

**Q. 컴파일러 드롭다운에 "GNU GCC"가 안 보이거나 비활성화되어 있어요.**
서버가 실행 중인 컴퓨터에 실제 GNU GCC가 설치되어 있지 않다는 뜻입니다. macOS는
`brew install gcc`로 설치할 수 있습니다 (설치되는 실행 파일 이름이 `gcc-16`처럼 버전이 붙어서
`backend/src/main/resources/application.yml`의 `compiler.options` 후보 목록에 없는 새 버전이면
목록에 그 버전을 추가해야 인식됩니다). Ubuntu 등 Linux는 보통 `sudo apt-get install gcc`로 충분합니다.

**Q. "실행 시간"이 매번 값이 조금씩 달라져요.**
프로세스를 새로 띄워서 실행하는 방식이라 OS 스케줄링 등의 영향을 받습니다. 그래서 5번 실행해서
그중 최솟값을 보여주도록 되어 있지만(노이즈를 줄이기 위함), 그래도 완전히 통제된 벤치마크 환경은
아니라서 어느 정도의 변동은 정상입니다. 큰 흐름(예: O0이 O2/O3보다 눈에 띄게 느림)을 보는 용도로
쓰는 것을 권장합니다.

**Q. 아주 긴 코드나 무한 루프를 넣으면 어떻게 되나요?**
코드는 20,000자까지만 허용됩니다. 컴파일이 10초 안에 끝나지 않으면 서버가 자동으로
중단시키고 "컴파일 시간 초과" 에러를 표시합니다. 실행 시간 측정을 켰는데 `main()` 안에
무한 루프가 있다면, 5초 안에 끝나지 않는 실행을 마찬가지로 강제 종료하고 "실행 시간 초과"로 표시합니다.

## 6. 알아두면 좋은 배경 지식

- `-O0`~`-O3`은 GCC/clang 계열 컴파일러의 **최적화 레벨** 옵션입니다. 숫자가 높을수록 더 적극적으로
  코드를 재구성하지만, 컴파일 시간이 늘어나고 디버깅은 더 어려워집니다.
- 실무에서는 개발 중에는 `-O0`(디버깅 쉬움), 배포할 때는 `-O2`(성능과 크기의 균형)를 주로 사용합니다.
- 이 앱에서 보여주는 "어셈블리"는 **AT&T 문법이 아니라 clang의 기본 출력(대상 아키텍처에 맞는 네이티브 어셈블리)**입니다.
  Apple Silicon(M1/M2/M3 등)에서 실행하면 ARM64 명령어가, Intel Mac에서 실행하면 x86-64 명령어가 나옵니다.
